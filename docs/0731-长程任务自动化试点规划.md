## 一、核心理念

### 1.1 什么是"长程任务自动化"

```
传统方式：  设计 → 一次性执行 → 完成/卡住 → 问人 → 继续
长程方式：  交互预热（冻结设计）→ 自动执行 → Policy 驱动决策 → 审计日志闭环
```

核心区别：**把"不确定性"在开始前消耗掉，执行阶段几乎不消耗人工注意力。**

### 1.2 为什么选 SPDT-005 做试点

SPDT-005 天然具备"长程任务"的结构：

| 长程任务要素 | SPDT-005 的对应实现 |
|:---|:---|
| 多阶段执行 | 5 阶段管线（ingest→structure→render→adapt→deliver）|
| 决策规则（Policy） | `content_type_registry.yaml` checkpoint 规则 |
| 质量门禁 | Stage 4 质量评分卡（≥70 分 PASS）|
| 审计闭环 | `PolicyAuditLogger` 决策事件记录 |
| 人类介入点 | M2/M6 checkpoint + 灰区规则 |
| 持久化产物 | 每阶段产出 JSON artifact |

而且 SPDT-005 已经包含第一个内容类型 `breakdown_news` 的完整实现，具备迭代对比的基础。

## 三、执行框架：三阶段迭代

### 阶段 1：交互预热（冻结设计）

**目标：用对话把"最大不确定性"消耗掉**

这是长程自动化最关键的步骤。开始写代码之前，先用对话把以下内容确定：

```
┌─────────────────────────────────────────────────────────────┐
│  交互预热检查清单                                            │
├─────────────────────────────────────────────────────────────┤
│  1. 内容类型的定位                                            │
│     - 解决什么问题？                                          │
│     - 受众是谁？                                              │
│     - 成功标准是什么？                                        │
│                                                             │
│  2. 数据来源（ingest）                                       │
│     - 数据从哪来？                                            │
│     - 触发条件是什么？                                        │
│     - 有哪些外部依赖？                                        │
│                                                             │
│  3. 结构设计（structure）                                    │
│     - 输出结构是什么？（大纲模板）                             │
│     - 核心知识节点有哪些？                                    │
│                                                             │
│  4. 语气与风格（render）                                     │
│     - 文学性维度（1-5）：                                    │
│     - 专业深度维度（1-5）：                                   │
│     - 有哪些禁止使用的表达？                                  │
│                                                             │
│  5. 质量标准（adapt）                                        │
│     - 最低分阈值是多少？                                      │
│     - 哪些维度是"一票否决"？                                  │
│                                                             │
│  6. 交付渠道                                                │
│     - 需要哪些 channel？（markdown/web/feishu...）            │
│     - 是否有特殊格式要求？                                   │
│                                                             │
│  7. 异常情况                                                │
│     - 哪些情况需要人工介入？                                   │
│     - 灰区触发规则是什么？                                    │
└─────────────────────────────────────────────────────────────┘
```

### 阶段 2：自动化执行（Policy 驱动）

**目标：代码实现 + 自动跑通 + 审计日志记录**

执行顺序：

```
Step 1: 编写 content_type_registry.yaml 配置
           ↓
Step 2: 实现 ingest 模块（radar_*.py）
           ↓
Step 3: 实现 structure 模块（article_*.py）
           ↓
Step 4: 实现 render 模块（render_*.py）
           ↓
Step 5: 实现 adapt 模块（scorecard_*.py）
           ↓
Step 6: 注册到 CONTENT_TYPE_MODULES（pipeline_router.py）
           ↓
Step 7: 运行 pipeline，采集审计日志
           ↓
Step 8: 分析 gap_events → 更新 Policy 规则 → 补规则
           ↓
Step 9: 跑通，验收测试通过
```

**Policy Gap 修复流程（每次运行后执行）：**

```
查看 policy_audit.jsonl
       ↓
发现 gap_events > 0？
       ↓ 是
分析 gap 事件类型：
  - route_fallback    → 在 registry 里注册该 content_type
  - checkpoint_hold  → 在 checkpoint 规则里加 "skip" 或提高阈值
  - quality_gate_failed → 调 LLM prompt 或降低阈值
  - decision_unmatched  → 在 Policy 规则表里补充该场景
       ↓
更新 registry / checkpoint 规则
       ↓
重新运行 pipeline
       ↓ 直到 gap_events = 0
```

## 五、工具支撑：audit_analyzer.py 规格

### 5.1 功能需求

```python
# 使用方式
python tools/audit_analyzer.py

# 输出
=== Policy Gap 分析报告 ===
Pipeline: PL_science_fact_abc123
Gap Events: 3
─────────────────────────────────
[1] decision_unmatched | stage=adapt | 原因: 科学引用数量不足时的策略未定义
    匹配规则: (无)
    建议: 在 scorecard_weights.science_fact 中增加 "citation_min" 规则

[2] quality_gate_failed | stage=adapt | score=58 < threshold=70
    匹配规则: M4:threshold_70
    建议: 调整 render prompt 或降低阈值至 65

[3] checkpoint_hold | stage=structure | ticket_id=CHK_STRUCTURE_xxx
    匹配规则: M2:confirm
    建议: 改为 M2:fast_confirm 或 M2:skip（若结构已模板化）
─────────────────────────────────
Policy 覆盖度评分: 78%
下一步行动: 补充 2 条决策规则后重新运行
```

### 5.2 核心逻辑

1. 读取 `policy_audit.jsonl`
2. 按 pipeline_id 分组
3. 筛选 `gap=True` 的事件
4. 按 event_type 聚合，统计频率
5. 根据 event_type 提供固定建议模板
6. 输出 Markdown 格式报告

## 六、关键设计原则（提炼自文档1）

| 编号 | 原则 | 在本项目中的体现 |
|:---|:---|:---|

## 七、风险与对策

| 风险 | 概率 | 对策 |
|:---|:---|:---|
| 某个内容类型的数据源无法 Mock | 中 | 先做 Mock 实现，真实数据源作为后续迭代 |
| LLM 输出不稳定导致评分卡分数波动大 | 高 | scorecard prompt 加入评分标准示例；阈值设宽 |
| 新类型和现有架构不兼容，需要重构 | 低 | 架构已预留扩展性，只需注册 + 写 4 个模块 |
| SOP 写得太理论，无法落地 | 中 | SOP 直接用 P0/P1 的真实复盘文档填充，不空写 |
| 审计日志过多难以分析 | 低 | `audit_analyzer.py` 自动聚合，同类事件去重 |
