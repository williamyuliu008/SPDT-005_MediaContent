> 版本：V1.1

## 一、设计背景与目标

### 1.1 原始方法论回顾

用户已沉淀一套完整的社科通俗作品全自动生产体系，核心逻辑为：

- **强约束 + 受控多样性**：LLM 不做作文题，只做选择题和填空题
- **六阶段流水线**：冷启动 → 选材 → 编排（COG+PDL）→ 对抗评审 → 受控生成 → 多模态输出
- **五大生产资料**：标签体系 / 模板库 / 知识库 / 文风包 / 读者画像
- **可审计性**：所有决策链路可回溯

### 1.2 本文档目标

将上述方法论翻译为**多智能体协作系统的架构设计**，解决三个核心问题：

1. 每个环节该由什么类型的智能体承担？
2. 智能体之间如何通信与协作？
3. 如何确保系统级的一致性、可审计性与可控性？

## 三、主编智能体（Chief Editor Agent）

### 3.1 角色定位

主编智能体是整个系统的**控制平面**，而非执行者。它不写内容，但决定：
- 哪个智能体在哪个阶段被激活
- 当前阶段产出的上下文如何传递给下一阶段
- 遇到冲突时如何决策

### 3.2 核心能力

```
ChiefEditor
├── 作品上下文管理器
│   ├── 当前 Series Profile（系列DNA快照）
│   ├── 当前 Book Config（单书配置快照）
│   ├── 已完成章节状态（已完成/待评审/待生成）
│   ├── 全局知识库指针（当前知识库版本）
│   └── 主编笔记（人工干预记录）
│
├── 流水线调度器
│   ├── phase_transition()    # 判断阶段是否可流转
│   ├── reroute()            # 评审不通过时 → 反思智能体 → 编排/生成智能体
│   └── parallel_gate()      # 并行章节的汇合点
│
├── 决策仲裁器
│   ├── author_override()    # 接收作者手动干预指令
│   ├── conflict_resolution() # 多智能体意见冲突时仲裁
│   └── quality_gate()       # 全局质量门槛判断
│
└── 审计日志写入器
    └── 记录所有调度决策 + 干预操作 + 流转原因
```

### 3.3 主编智能体的决策边界

**它做不了的事**：
- 不直接读写知识库（由选材/编排智能体代理）
- 不直接调用 LLM 生成内容（由生成智能体代理）
- 不修改文风包/史观包配置（由对应管理智能体代理）

**它只做的事**：
- 决定"谁在什么条件下做什么"
- 持有全局上下文快照，保证跨智能体一致性
- 写入审计日志，提供可回溯的决策链

## 四、冷启动智能体（Cold Start Agent）

### 4.1 职责

冷启动是系统一次性重投入阶段。该智能体负责**将专家经验翻译为可执行配置资产**，完成以下五件事：

1. **系列品牌配置（Series Profile）** → 写入配置文件
2. **史观参数包配置（Historiography Profile）** → 写入史观库
3. **读者画像配置（Reader Persona）** → 写入画像库
4. **文风包注册（Style Pack）** → 写入文风包库
5. **知识库初始化** → 知识节点入库 + 依赖图构建

### 4.2 与主编智能体的交互

```
主编智能体 ──[new_series_launch]──→ 冷启动智能体
                                      │
                                      ├── 询问：系列定位/目标读者/核心史观/参考文风
                                      ├── 生成：Series Profile YAML 草稿
                                      ├── 等待：主编确认（或作者微调）
                                      └── 返回：冷启动完成报告 + 配置快照ID
```

### 4.3 子任务分解

该智能体内部可分解为三个子角色协作：

| 子角色 | 任务 |
|--------|------|
| `SeriesArchitect` | 构建 Series Profile，主旋律变奏策略，品牌标识 |
| `ProfileIngestor` | 接收结构化史观参数包，校验五维立场向量合理性 |
| `StyleReverseEngineer` | 可选：若需从标杆作品逆向提取文风包，触发文风包逆向流程 |

### 4.4 关键设计点

- 冷启动完成后，系统生成**配置快照 ID**，后续所有流水线引用此快照
- 快照版本化管理，支持回滚
- 文风包和史观包配置完成后须通过**一致性校验**（禁止词表不与价值观关键词冲突）

## 五、选材智能体（Material Scout Agent）

### 5.1 职责

从知识库中按照当前章节的叙事意图，挑选最适合的知识点组合。核心是**选材评分公式**的执行。

### 5.2 核心流程

```
输入：叙事意图 + 史观包 + 读者画像 + 当前章节需求
           │
           ▼
    ┌──────────────────┐
    │  候选节点召回    │ ← 从知识库按标签召回候选节点
    └────────┬─────────┘
             │ ← 若召回为空，启动"挖掘模式"
             ▼
    ┌──────────────────┐
    │  挖掘模式（Fallback）│ LLM 扫描原始史料，动态识别
    │  ·dramatic_irony  │  潜在戏剧性/反讽性/结构性矛盾
    │  ·moral_dilemma   │  动态生成标签，不依赖预标注
    │  ·structural_contradiction│
    │  ·relations图谱推理│  利用precedes/contradicts字段推理
    └────────┬─────────┘
             ▼
    ┌──────────────────┐
    │  五维加权评分    │ S = α·IntentFit + β·DramaticPotential
    │                  │     + γ·SourceQuality + δ·ReaderResonance
    │                  │     + ε·HistoriographyBias
    └────────┬─────────┘
             ▼
    ┌──────────────────┐
    │  五项约束过滤    │ 覆盖均衡/时间顺序/多视角/
    │                  │ 戏剧密度上限/来源最低要求
    └────────┬─────────┘
             ▼
    ┌──────────────────┐
    │  节点序列输出    │ [node_01, node_03, node_07, ...]
    └────────┬─────────┘
             ▼
    ┌──────────────────┐
    │  作者干预接口    │ 接收 boost/pinned/excluded 指令
    └──────────────────┘
```

### 5.4 与编排智能体的边界

选材智能体**只决定"讲什么"**（知识点序列），**不决定"怎么讲"**（模板、章节结构）。

## 六、编排智能体（Orchestration Agent）

### 6.1 职责

编排是整个系统中最复杂的环节。它接收选材结果，输出**章节级导演分镜脚本（COG JSON）**，包含：选用模板、章节角色序列、张力曲线、钩子布局、冲击力投放点、主旋律变奏设计。

### 6.2 核心流程：三层漏斗 + PDL 增强

```
选材结果（节点序列）
        │
        ▼
┌─────────────────────────────────┐
│  Layer 1：硬性过滤               │
│  按模板 precondition 淘汰不匹配   │
│  输出：2-3 个候选模板            │
└───────────────┬─────────────────┘
                ▼
┌─────────────────────────────────┐
│  Layer 2：加权评分               │
│  FinalScore = 0.4×LabelOverlap  │
│  + 0.25×StructuralFit           │
│  + 0.2×NarrativePotential       │
│  + 0.1×SourceRichness           │
│  + 0.05×HistoriographyMatch     │
└───────────────┬─────────────────┘
                ▼
┌─────────────────────────────────┐
│  Layer 3：语境修正               │
│  章节位置加成/前后文去重/        │
│  史观参数调整                    │
└───────────────┬─────────────────┘
                ▼
        ┌────────────────┐
        │ 模板确定 + 角色指派 │
        └───────┬────────┘
                ▼
    ┌──────────────────────────┐
    │  降级策略（Fallback）       │  ← 新增
    │  若 top2 得分差 < 0.05     │
    │  或 Layer 3 后无唯一胜出   │
    │  → 默认采用安全模板：        │
    │    TPL-01（开篇/中间章节） │
    │    TPL-09（结尾章节）      │
    │  标记 Warning，不阻断流程   │
    └───────────────┬────────────┘
        └───────┬────────┘
                ▼
┌─────────────────────────────────┐
│  PDL 增强                        │
│  ·张力阶梯标注（0-1 量表）        │
│  ·高潮位置 + 节奏标记            │
│  ·六大钩子槽位布局               │
│  ·冲击力投放点标记               │
│  ·主旋律变奏位置                 │
│  ·密度量化：高低密度由模板ID决定  │
│    high=[TPL-03,06,09]           │
│    medium=[TPL-01,04,05]         │
│    low=[TPL-07,10]               │
│    禁止连续下降（除刻意制造虚假安全）│
└───────────────┬─────────────────┘
                ▼
         COG 章节脚本 JSON
```

### 6.4 编排校验引擎

编排输出须通过五项校验，否则阻断并返回修正建议：

1. 角色唯一性（每个章节角色不重复指派）
2. 张力单调性（无标记不得连续下降）
3. 过渡合法性（如 temporal_expansion 前后 scale 必须满足约束）
4. 节奏呼吸（高密度后必须有呼吸段）
5. 史观一致性（所有 section 文风包与章节史观兼容）

### 6.5 密度量化算法（呼吸感工程化）

密度不由字数决定，由**模板类型**决定：

| 密度级别 | 模板 | 校验规则 |
|---------|------|---------|
| high | TPL-03（制度杀人）、TPL-06（观念诞生）、TPL-09（长时段） | 高密度后必须跟 medium 或 low |
| medium | TPL-01（小事撬动）、TPL-04（文明碰撞）、TPL-05（技术改变） | 连续3个后必须插入 low |
| low | TPL-07（被遗忘的多数）、TPL-10（复调历史） | 仅作呼吸节拍，不可连续 |

### 6.6 COG 可视化调试工具（开发期必备）

**COG Visualizer** 是编排智能体的调试伴侣，非生产依赖项：

- 输入：COG JSON 脚本
- 输出：类似钢琴卷帘的时间轴视图
  - 横轴：章节结构（单元序列）
  - 纵轴：张力曲线（0-1 折线图）
  - 色块：密度级别（高/中/低）
  - 标记：钩子位置、高潮节点、冲击力投放点、主旋律变奏
- 功能：人工 Debug、预览张力弧线、验证过渡衔接
- 上线顺序：**先有可视化，再上自动化**

## 七、评审智能体（Adversarial Review Agent）

### 7.1 角色定位

评审智能体是一个**多角色容器**，内部包含五个专门评审 Agent。它不创作，只攻击——用预设的规则和 LLM 判断当前编排脚本或生成文本是否达到质量门槛。

### 7.2 五大评审 Agent

| Agent | 攻击角度 | 评判标准来源 |
|-------|----------|-------------|
| 史观审计员 | 立场漂移、禁词命中、情绪基调一致性 | 当前史观参数包 |
| 读者代言人 | 知识门槛、类比失效、情感错位、抵触触发 | 当前读者画像 |

### 7.4 三级对抗强度

| 等级 | 触发时机 | 参与 Agent | 宽容度 |
|------|---------|-----------|--------|
| 轻度 | 草稿自检 | 规则引擎（关键词/张力曲线） | 宽松 |
| 中度 | 内部打磨 | 规则 + 史观审计员 + 读者代言人（LLM） | 标准 |
| 重度 | 出版前终审 | 全部 5 个 Agent | 严格 |

### 7.5 评审宽容度参数（review_strictness）

在 **Series Profile** 中新增可配置参数，控制评审严格程度：

```yaml
review_config:
  review_strictness: "medium"  # loose | medium | strict
  # loose: Error 阻断，Warning 通过；medium: Error 阻断，Warning 参考；strict: Error+Warning 均阻断
  max_revision_loops: 3        # 修订循环上限，超限→人工干预
  confidence_threshold: 0.6     # 置信度低于此值的 Warning 不阻断流程
```

### 7.6 置信度加权机制

每个评审 Agent 的输出包含 `confidence` 字段（0.0-1.0）：

```json
{
  "agent": "reader_advocate",
  "passed": false,
  "confidence": 0.72,
  "issues": [
    {
      "severity": "warning",
      "confidence": 0.65,
      "issue": "类比对象可能偏高阶",
      "suggestion": "调整为更通俗的类比"
    }
  ]
}
```

处理规则：
- `severity: error` 且 `confidence ≥ 0.5` → **阻断**
- `severity: warning` 且 `confidence ≥ 0.6` → **Warning 记录**，不阻断
- `severity: warning` 且 `confidence < 0.6` → **低置信度参考**，仅记录，不计入阻断判断

### 7.5 循环设计

评审不通过时，主编智能体将评审报告发送给**反思智能体**（解读评审）→ 生成修改指令 → 发回编排/生成智能体修订。修订后重新提交评审，循环最多 3 次。3 次不通过则进入人工干预通道。

> **反思智能体**不创作也不攻击，专门做"翻译"工作：把抽象的评审意见（如"情感连接点偏高"）翻译为具体的修改指令（如"将 sec_02.analogy_slot 的 analogy_source_domain 从 corporate_executive 改为 office_middle_manager"）。

## 八、生成智能体（Controlled Generation Agent）

### 8.1 职责

执行 LLM 填槽，这是系统中**唯一直接调用大语言模型**的环节。核心原则：LLM 不创作，只填空。

### 8.2 四层注入架构

```
输入：COG 脚本 + 知识节点上下文 + 文风包 + 史观包 + 读者画像
          │
          ▼
┌─────────────────────────────────┐
│  Layer 1：史观注入               │
│  → system_prompt               │
│  ·HP.stance_vector 描述          │
│  ·HP.forbidden → negative_prompt│
│  ·HP.emotional_tone → tone     │
└───────────────┬─────────────────┘
                ▼
┌─────────────────────────────────┐
│  Layer 2：读者连接点注入         │
│  → cognitive_bridge_slot        │
│  → emotional_bridge_slot        │
│  ·analogy_pool 搜索匹配类比      │
│  ·emotional_tone 匹配共鸣标签   │
└───────────────┬─────────────────┘
                ▼
┌─────────────────────────────────┐
│  Layer 3：文风包注入             │
│  → fill_instruction            │
│  ·Lexical Pool → 词汇约束       │

└───────────────┬─────────────────┘
                ▼
┌─────────────────────────────────┐
│  Layer 4：冲击力+主旋律注入      │

                │
                ▼
    ┌─────────────────────┐
    │  输出后校验          │
    │  ·forbidden 命中检测 │
```

### 8.3 填槽指令标准格式

```json
{
  "slot_id": "sec_02.structure_unit.analogy_slot",
  "slot_type": "cognitive_bridge",
  "constraints": {
    "style_pack_id": "cp_history_huang_renyu_v1",
    "forbidden_words": ["令人震惊", "不可思议", "昏庸"],
    "tone": "calm_analytical_with_subtle_irony",
    "max_chars": 180,
    "analogy_source_domain": ["corporate_structure", "office_politics"]
  },
  "slot_prompt": "用明代内阁的运作逻辑，生成一个帮助读者理解'技术治理真空'的类比。类比对象应为现代职场/管理场景，控制在180字以内。",
  "knowledge_context": {
    "node_id": "event_wanli_15_申时行奏折",
    "node_summary": "万历十五年，文官集团与皇权陷入结构性僵局，首辅申时行试图调和",
    "structural_insight": "道德治国与技术治理的张力"
  },
  "tension_context": {
    "current_tension": 0.7,
    "target_tension": 0.85,
    "tension_label": "dramatic_irony"
  }
}
```

### 8.4 多轮填槽协调

一个章节通常包含 3-5 个 section，每个 section 包含 3-6 个填槽点。生成智能体负责：
- 维护填槽进度状态
- 按依赖顺序调度（部分 slot 依赖前序 slot 输出）
- 聚合所有 slot 输出为完整章节文本
- 处理 slot 级别的重试（格式错误 → 重试 2 次 → 使用 fallback 文本）

### 8.5 上下文感知填充（Context-Aware Filling）

**重要修正**：各 Slot 不独立。前序 Slot 的输出内容会影响后续 Slot 的指代连贯性和逻辑衔接。

```yaml
slot_chain:
  dependency: ordered  # 按章节结构顺序填槽
  prefix_context: true  # 后续 Slot 接收前序已填充文本作为上下文
  coherence_check:
    enabled: true
    checks:
      - "代词指代一致性（前序人名/地名不丢失）"
      - "逻辑连接词衔接（因→果、转折→然而）"
      - "概念首次引入后不再重新定义"
    fallback: "若前序 Slot 缺失，插入简短承接句"
```

### 8.6 流式输出与 Forbidden 打断

生成智能体支持流式 LLM 调用（streaming: true），在检测到 Forbidden Words 时立即中断并重试：

```yaml
streaming_config:
  enabled: true
  forbidden_interrupt:
    enabled: true
    check_interval: "token"  # 每生成一个 token 检查一次
    action_on_hit: "interrupt_and_retry"
    max_retries: 2
    fallback: "使用 fallback 文本，跳过该 slot"
  token_budget:
    max_tokens_per_slot: 500
    max_tokens_per_chapter: 20000
    budget_alert_threshold: 0.8  # 消耗80%后告警
```

### 8.7 Token 计数器与成本监控

生成智能体内置 Token 计数器，每次 LLM 调用记录消耗：

```json
{
  "token_record": {
    "chapter_id": "ch03",
    "slot_id": "sec_02.structure_unit",
    "input_tokens": 1234,
    "output_tokens": 456,
    "total_tokens": 1690,
    "cost_estimate_usd": 0.0034,
    "running_chapter_total": 8432
  }
}
```

主编定期汇总各章节 Token 消耗，超预算则触发告警并可选择降级到小模型。

## 十一、通信协议设计

### 11.1 智能体间通信原则

1. **主编智能体居中路由**：所有流水线节点之间的通信经由主编，不允许编排直接呼叫生成
2. **上下文传递携带 schema**：每次流转携带类型化的上下文对象，而非自由文本
3. **指令 + 数据分离**：主编发送的是**指令**（做什么），生成智能体执行的是**数据**（填槽内容）

## 十四、非功能需求

### 14.0 Error Code 标准化（工程化必备）

所有异常必须携带标准 Error Code，智能体根据 Code 执行对应恢复策略：

| Error Code | 含义 | 恢复策略 |
|-----------|------|---------|
| `ERR_NO_TEMPLATE_FOUND` | 三层漏斗无候选模板 | 启动安全模板降级（TPL-01） |
| `ERR_REVIEW_LOOP_MAX` | 修订循环达到上限 | 触发人工干预通道 |
| `ERR_LLM_SAFETY_TRIGGER` | LLM 输出触发安全词/内容 | 立即打断，重试或用 fallback |
| `ERR_SELECTION_MINING_FAIL` | 挖掘模式扫描原始史料失败 | 返回空结果，提示人工补充标签 |
| `ERR_FORBIDDEN_WORD_LEAK` | 输出后校验发现 Forbidden Word | 自动替换，重试，最多重试2次 |
| `ERR_TOKEN_BUDGET_EXCEED` | Token 消耗超出预算 | 降级到小模型，或使用 fallback 文本 |
| `ERR_STYLE_JS_DIVERGENCE` | 风格偏离 JS 散度 >0.15 | 强制使用 Top-1 词汇而非随机 |
| `ERR_REVIEW_CONFLICT` | 多评审 Agent 意见冲突 | 主编仲裁，优先置信度高的一方 |
| `ERR_SNAPSHOT_INCONSISTENT` | 快照读取与预期不符 | 重新加载最新快照，重试 |

### 14.1 性能目标

| 指标 | 目标值 |
|------|-------|
| 单章节冷启动 → 首版文本 | ≤15 分钟（并行章节可压缩） |
| 选材 → 编排 → 评审（轻度）全流程 | ≤3 分钟 |
| 多模态派生（同一章节换文风包） | ≤1 分钟 |
| 断点续生产能力 | 任意节点重启，读快照即可恢复 |
| Token 消耗告警 | 章节超 20000 tokens 触发提示 |

### 14.1.1 幂等性要求

断点续跑依赖每个智能体的**幂等输出**：
- 在相同 Snapshot ID + 相同输入下，多次运行产生结果一致（允许 LLM 采样范围内的词汇差异）
- 规则引擎阶段（选材/编排）必须完全幂等
- 生成阶段因 LLM 采样天然存在差异，但 Slot 输出缓存后不重复调用
- 幂等性是调试和回归测试的基础

### 14.2 可扩展性

| 扩展维度 | 实现方式 |
|---------|---------|
| 新增叙事模板 | 注册 TPL-11 YAML（precondition + 亲和度矩阵），自动纳入三层漏斗 |
| 新增评审 Agent | 注册 agent YAML（攻击角度 + 评判标准来源），主编路由自动纳入 |
| 新增文风包 | 注册 Style Pack YAML，五层注入引擎自动支持 |
| 跨领域扩展 | 新建知识库 + 新建文风包 + 复用全部引擎 |

### 14.3 人机协作界面（主编操作台）

系统不能只有 API，必须提供 Web UI 供主编操作。核心功能：

| 功能 | 说明 |
|------|------|
| 快照时间轴 | 可视化已完成章节状态，支持拖拽回滚到任意版本 |
| 评审报告可视化 | 高亮问题文本，显示每条 issue 的位置/维度/严重度/置信度 |
| 干预指令输入 | Pin/Boost/Exclude 可视化下注，附带原因记录 |
| 选材预览 | 知识节点打分明细可视化，支持人工调权 |
| Token 消耗看板 | 各章节 Token 消耗排行榜，预算告警 |
| COG 脚本预览 | COG Visualizer 集成，可实时查看张力曲线 |
| Error Log | 实时显示 Error Code 及对应恢复策略执行状态 |

### 14.4 多模型兼容

- 所有 LLM 调用通过统一接口 `llm_call(slot_instruction)` 代理
- 换模型仅需修改 adapter 层，不影响模板/文风包/规则引擎
- 模型切换后执行回归测试（风格 JS 散度、禁止词命中率）

## 十六、实施优先级建议

### Phase 1：核心闭环（主编 + 选材 + 编排 + 生成）

最小可行系统只需 4 个智能体：
1. 主编智能体（协调 + 路由）
2. 选材智能体（知识库查询 + 评分，含挖掘模式）
3. 编排智能体（三层漏斗 + 降级策略 + COG 输出）
4. 生成智能体（LLM 填槽 + 上下文感知 + 流式打断）

**交付物**：给定知识节点 + 模板，手动传入意图，可输出完整章节草稿。

> **审核意见落地**：Phase 1 还需包含 **COG Visualizer**（可视化调试工具），先可视化再自动化。这是调试编排逻辑的必备工具。

### Phase 2：评审接入（+ 评审智能体 + 反思智能体）

接入轻度对抗评审（规则引擎），建立自动化质量门禁。
- 评审宽容度参数（review_strictness）配置
- 置信度加权机制
- 反思智能体：评审报告 → 具体修改指令
- Error Code 标准化（重点 ERR_REVIEW_LOOP_MAX）

### Phase 3：冷启动体系化（+ 冷启动 + 支撑型智能体 + 合规扫描）

将手动配置改为智能体协作的半自动冷启动流程。
- 文风包逆向工程辅助工具（标杆文本 → 初步 YAML）
- 史观包版本 Diff 可视化（影响章节回归测试）
- 合规扫描智能体：配置升级后自动扫描受影响存量章节
- Token 计数器与成本看板

### Phase 4：多模态扩展（+ 输出智能体）+ 主编操作台

- SSML 音频脚本生成
- 动画分镜标签生成
- 主编操作台 Web UI（快照时间轴、评审可视化、干预指令、Token看板）

---

> **本设计将社科创作方法论翻译为多智能体协作系统：主编居中协调，选材/编排/评审/生成各司其职，支撑型智能体按需服务，全部决策链路可审计、可回滚、可扩展。**
